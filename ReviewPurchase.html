1. Workflow tổng quan

1.1. Path A — PO-driven (luồng chuẩn)

PO Draft → Submitted → Approved → [Receive] → Receiving → Completed
                                       ↓
                          GoodsReceipt(SourceType=FromVendor, linkedPoId)
                                       ↓ (event GoodsReceiptCreated)
                                  +Stock  +VendorDebt (nếu đủ cost+vendor)
                                       ↓
                          VendorReturn(linked GR | PO | free) → Inspecting → Confirmed
                                       ↓ (event VendorReturnConfirmed)
                          DeliveryNote(SourceType=ToVendorReturn, Status=Delivered)
                          → -Stock  -VendorDebt (FIFO)  +Expense (additionalCost)

1.2. Path B — GR-driven (luồng phụ trợ)

GoodsReceipt độc lập (no PO) → SetGoodsReceiptToPurchaseOrder
                                       ↓
                          Match items theo (ProductId, UnitCost)
                          ├─ Exact match: update PO.Item.QuantityReceived
                          └─ Partial (GR no cost): split GR item + set cost từ PO

1.3. Trạng thái

EntityStatesTransition rules
PurchaseOrder Draft (10) → Submitted (20) → Approved (30) → Receiving (40) → Completed (50). Cancelled (60) khả thi từ bất kỳ trạng thái nào trừ Completed/Cancelled, và chỉ nếu không có item nào đã nhận. One-way (không quay lùi). Cancel block khi có QuantityReceived > 0.
GoodsReceipt Không có status — chỉ có lifecycle: tạo → (set vendor / set unit cost) → delete (soft). Delete bị block nếu có Confirmed VendorReturn liên kết hoặc stock đã bị Reserve.
VendorReturn Draft (0) → Inspecting (1) → Confirmed (2). Cancelled (3) từ Draft/Inspecting. Confirmed = no undo. Cancel chỉ từ Draft/Inspecting.

2.2. Concurrency race khi 2 user cùng nhận 1 PO

PurchaseOrderManager.ReceiveItemsAsync / BulkReceiveItemsAsync
  • Flow: đọc PO → check QuantityReceived + receivingQty <= QuantityOrdered → cộng dồn → Update.
  • Không có RowVersion / [Timestamp] / optimistic concurrency token trên PurchaseOrder entity. EF default không chặn race.
  • 2 request đồng thời (vd user kho A và user kho B cùng nhận) có thể vượt qty — last-write-wins overwrites check.
  • Tác động: data integrity. Có thể nhận quá số đặt mà không bao giờ phát hiện.
P0

2.3. VendorReturn Draft/Inspecting KHÔNG reserve qty trả

VendorReturnManager.ConfirmAsync (validate aggregate chỉ ở step Confirm)
  • Aggregate-validate qty (previouslyReturned + currentRequest <= received) chỉ ở ConfirmAsync.
  • Kịch bản fail:
    1. GR có 10 item X.
    2. User A tạo VR_Draft trả 5/10 (chưa Confirm).
    3. User B tạo VR_Draft trả 6/10 (chưa Confirm). Pass vì chưa có Confirmed nào.
    4. Cả 2 Confirm cùng lúc → một trong hai fail tại Confirm; user mất công nhập thừa.
  • Cột "Đã trả" trong Details của GR/DN chỉ tính Confirmed → user mù về phần đang giữ ở Draft/Inspecting.
  • Tác động: UX kém + race window khi confirm đồng thời.

4. Design weaknesses

P2

4.1. PO không hỗ trợ cost-per-receive

  • 1 PO item = 1 UnitCost cố định. Bulk-receive luôn dùng cost của PO item.
  • Thực tế: NCC bù trừ giá lúc giao, hoặc CK theo lô → giá khác giá đặt.
  • Hệ quả: AverageCost của Product không phản ánh giá thực.
  • Workaround hiện tại: tạo GR độc lập (Path B) rồi link sau — nhưng split-cost logic phức tạp (xem 3.2).
  • Đề xuất: thêm ActualUnitCost override ở GoodsReceiptItem level, default = PO item cost.
P2

4.2. GoodsReceipt không có business code

  • GoodsReceipt chỉ có Id Guid, không có Code. User chỉ thấy date ReceivedOnUtc.
  • Khó reference giữa các bộ phận ("phiếu nhập ngày 10/05 lúc 09:00"... có khi 5 phiếu cùng ngày).
  • VendorReturn có Code (TNCC-YYYYMMDD-NNN) → inconsistency.
  • Đề xuất: thêm Code format PN-YYYYMM-NNN (Phiếu Nhập).

6. Tổng kết

Đánh giá tổng thể

Workflow happy path chạy đúng và có defense-in-depth (validate ở entity, app service, manager). Side effects qua MediatR events tách bạch rõ ràng (stock, debt, expense). Tuy nhiên có 4 vấn đề critical cần xử lý gấp:

  • Concurrency: chưa có cơ chế chống race ở PO level → rủi ro vượt qty khi nhận đồng thời.
  • Reversibility: Path B unlink chưa implement; VendorReturn Confirmed = no undo; GR delete có thể không rollback VendorDebt.
  • Visibility: Draft/Inspecting VR không reflected trong "Đã trả" → user mù thông tin pending.
  • Cost model: PO chốt giá lúc đặt, không cho override khi nhận → AverageCost lệch so với giá thực.

Ưu tiên xử lý P0 trước (data integrity), sau đó P1 (UX/business). P2/P3 có thể đưa vào roadmap dài hạn.
